# QDN Resource Strategy

This document defines the publishing strategy for migrated WordPress datasets. It is intentionally conservative: the importer prepares resources and logs, while real QDN publishing happens through a small Migration Publisher Q-App opened inside Qortal UI.

## Goals

- Keep imported WordPress content readable as independent Qortal-native JSON resources.
- Avoid publishing one large website ZIP as the primary content model.
- Publish media as separate QDN resources so posts can reference stable media identifiers.
- Keep enough source metadata to rebuild indexes, troubleshoot imports, and map old WordPress URLs to new QDN resources.
- Make the same dataset usable by the local viewer first and a Qortal Q-App later.

## Services

| Content | QDN service | Notes |
| --- | --- | --- |
| Post JSON | `DOCUMENT` | One resource per post. |
| Page JSON | `DOCUMENT` | One resource per page. |
| Index JSON | `DOCUMENT` | Posts, pages, categories, tags, media map, URL map, manifest. |
| Images | `IMAGE` | Downloaded images only. |
| Video | `VIDEO` | Downloaded video files when size is acceptable. |
| Audio | `AUDIO` | Reserved for downloaded audio files. |
| Documents and other files | `FILE` | PDF, ZIP, DOC, and other non-media files. |

## Identifier Rules

Identifiers are generated by `src/preparePublish.js`.

Current rules:

- Maximum identifier length: `64` characters.
- Post identifiers: `<prefix>-post-<slug-part>-<hash>`.
- Page identifiers: `<prefix>-page-<slug-part>-<hash>`.
- Media identifiers: `<prefix>-media-<filename-part>-<hash>`.
- Index identifiers:
  - `<prefix>-posts-index`
  - `<prefix>-pages-index`
  - `<prefix>-categories`
  - `<prefix>-tags`
- `<prefix>-media-map`
- `<prefix>-url-map`
- `<prefix>-import-manifest`
- `<prefix>-qdn-manifest`

The profile defines `<prefix>`. The generic profile uses `wpq`. The hash suffix
makes identifiers stable and avoids collisions when two resources have similar
slugs or filenames.
Converted JSON filenames separately include the WordPress source ID:

```text
<slug>--wp-<source_id>.json
```

## Publish Order

The first publishing command should publish in this order:

1. Media resources.
2. Post resources.
3. Page resources.
4. Index resources.

Reason: posts and pages can safely reference media only after media identifiers are known. Indexes should be published last because they represent the current complete dataset state.

## Resource Mapping

The publish command should update:

```text
wp-qortal-import/publish-log/published-resources.json
```

Each successful publish entry should include:

```json
{
  "type": "post",
  "service": "DOCUMENT",
  "identifier": "wpq-post-example-abc123",
  "local_path": "converted/posts/example.json",
  "qdn_name": "ExampleName",
  "published_at": "2026-05-28T00:00:00.000Z",
  "transaction_id": null
}
```

Failed entries should be appended to:

```text
wp-qortal-import/publish-log/errors.json
```

## QDN Name

The technical publishing Qortal name is not hard-coded. Qortal requires each QDN
resource name to be owned by the account signing the publication. The public
editorial author is deliberately separate from the technical QDN publisher.

Before real publishing, add a configuration value:

```env
QORTAL_NAME=
QORTAL_SITE_NAME=
QORTAL_CONTENT_NAME=
QORTAL_MEDIA_NAME=
QORTAL_PUBLISHER_NAMES=
QORTAL_COAUTHOR_NAMES=
PUBLIC_AUTHOR_NAME=
QORTAL_NODE_URL=http://localhost:12391
QORTAL_API_KEY=
QORTAL_API_KEY_FILE=~/qortal/apikey.txt
```

`QORTAL_NAME` is the Qortal name used by the current publishing session.
`QORTAL_SITE_NAME` is the stable website address and canonical CMS catalog name.
`QORTAL_CONTENT_NAME` is the stable publisher for migrated posts, pages, indexes,
images and documents.
`QORTAL_MEDIA_NAME` optionally routes downloaded audio and video resources to a
separate registered Qortal name. Images and documents stay with the content
publisher so the essential follow mode remains useful.
`QORTAL_PUBLISHER_NAMES` is a comma-separated registry of technical
publisher names. `PUBLIC_AUTHOR_NAME` controls the visitor-facing byline and
defaults to the active profile value.
`QORTAL_COAUTHOR_NAMES` is a comma-separated CMS coauthor registry seed.

The publish command should refuse to run when `QORTAL_NAME` is empty.
Direct node upload checks and future direct-node publishing require `QORTAL_API_KEY`.
For local development, prefer `QORTAL_API_KEY_FILE` so the API key is read from the Qortal install directory and not stored in the project.

## Migration Preview Loading Strategy

The local Migration Preview currently reads:

```text
/qortal-content/converted/posts-index.json
/qortal-content/converted/posts/<slug>.json
/qortal-content/media/...
```

The QDN mode replaces local paths with QDN lookups using:

```text
SERVICE + NAME + IDENTIFIER
```

The Q-App should start by loading:

```text
DOCUMENT + NAME + <prefix>-qdn-manifest
```

That manifest maps:

- `converted/<path>` to QDN service and identifier
- source media URL to QDN service and identifier
- known entrypoint indexes to their QDN identifiers

The important boundary is:

- Local development uses filesystem-backed `/qortal-content/`.
- Qortal production uses QDN-backed resources.
- The content JSON structure should stay the same.

Each manifest resource reference can include its own `name`. This allows a merged
catalog published under `ExampleSite` to resolve essential archive resources
published under `ExampleContent` and large media resources published under
`ExampleMedia`.

The merged catalog retains `publisher_names` for technical provenance while
`public_author` remains the editorial byline shown to visitors.

For a split publishing profile, publish the website and CMS catalog under a
stable site name, publish essential archive resources under a stable content
name, and reserve a dedicated media name for audio and video. Contributor names
can stay in the CMS coauthor registry without becoming public resource
dependencies.

The current Migration Preview supports both loader modes:

```text
/
```

loads local content.

```text
/?source=qdn&name=<QortalName>
```

loads `DOCUMENT/<QortalName>/<prefix>-qdn-manifest` first and then resolves all
indexes, posts, pages, and media through that manifest.

Local development can open the Migration Publisher with:

```text
/?tool=publish&name=<QortalName>
```

The normal production workflow builds a small Q-App ZIP:

```bash
npm run package:migration-qapp
```

The ZIP is published to Qortal as an `APP` or `WEBSITE`. Inside Qortal UI, the user selects the local `wp-qortal-import` folder. The Q-App reads local files through the browser folder picker and delegates signing and publishing to Qortal UI. The Node.js CLI does not ask for or store a private key.

Selected resources are sent with:

```text
qortalRequest({ action: 'PUBLISH_MULTIPLE_QDN_RESOURCES', resources: [...] })
```

Publisher modes:

- `Demo` publishes one small smoke-test set.
- `CMS JSON` publishes imported posts, pages, indexes, and one image for basic media testing.
- `Images` publishes images only.
- `Documents` publishes PDFs and other document/file resources.
- `Audio` publishes audio only.
- `Video` publishes video only.
- `Selected media` exposes checkboxes for manual batches.
- `Full media` publishes every planned resource, including all downloaded media files.

The publisher keeps local browser history and supports `Skip already published`. When enabled, it checks QDN and avoids uploading an existing `NAME + SERVICE + IDENTIFIER` resource again.

## External Linked Media

External linked media is not automatically published in the first strategy.

Current behavior:

- Downloaded same-site media is publishable.
- Third-party linked media stays in `linked_only_media`.
- The viewer keeps those links external unless they are manually downloaded and mapped later.

This prevents the demo import from silently copying third-party files.

## CLI Dry Run And Browser Publish

The CLI validates the plan:

```bash
npm run publish -- --dry-run
npm run publish -- --dry-run --check-node
```

Current behavior:

- `npm run publish -- --dry-run` validates the generated publish plan.
- `npm run publish -- --dry-run --check-node` also checks node status and temporary upload space.
- Real CLI publishing intentionally fails until a safe direct-node publishing path is confirmed.
- Real QDN publishing is available through the Migration Publisher Q-App in Qortal UI.

The Qortal node API can build unsigned ARBITRARY transactions through `/arbitrary/...` endpoints. A browser Q-App normally uses `qortalRequest({ action: 'PUBLISH_QDN_RESOURCE', ... })`, which delegates signing and publishing to Qortal UI. A Node.js CLI publisher must therefore either integrate a safe signing path or hand publishing off to a Qortal UI/Q-App workflow.

Expected future direct CLI publish behavior:

- `--dry-run` prints planned actions and validates local files.
- Real publish posts data to the local Qortal node API.
- Every success is logged immediately.
- Every failure is logged without stopping the whole batch unless the failure is configuration-related.
- Re-running the command skips resources that are already marked as published unless `--force` is used.
